# 5월 식품들의 총매출 조회하기

## 문제 요약
> `FOOD_PRODUCT`와 `FOOD_ORDER`를 조인해 **생산일자(`PRODUCE_DATE`)가 2022년 5월**인 주문만 대상으로, **상품별 총매출(PRICE × AMOUNT)**을 집계해 정렬한다.

## 느낀점
>
- 정리해둔 개념 여러 번 읽어보기

## 코드
```sql
SELECT FP.PRODUCT_ID, FP.PRODUCT_NAME, SUM(FP.PRICE * FO.AMOUNT) AS TOTAL_SALES
FROM FOOD_PRODUCT FP
JOIN FOOD_ORDER FO ON FP.PRODUCT_ID = FO.PRODUCT_ID
WHERE FO.PRODUCE_DATE LIKE '2022-05%'
GROUP BY FP.PRODUCT_ID, FP.PRODUCT_NAME
ORDER BY TOTAL_SALES DESC, FP.PRODUCT_ID;
```

## 질문 & 실수 정리

### 질문했던 내용 (새로 배운 것)

#### 1. `FOOD_ORDER`에 같은 `PRODUCT_ID`가 여러 행으로 존재할 때 집계가 되는 이유
- `FOOD_ORDER`는 **주문 “행(ROW)” 단위**로 `PRODUCT_ID`와 `AMOUNT`를 가진다.
- 따라서 같은 상품이 여러 주문행에 반복될 수 있고, 조인 후 **상품 기준으로 묶어(`GROUP BY`) 합계(`SUM`)**를 내면 상품별 총매출이 계산된다.
- 예시처럼 `P0017`이 2건 주문되면, `PRICE × (1200 + 1000)`처럼 **한 상품으로 합쳐져 1행**으로 나온다.

#### 2. 집계함수와 `GROUP BY` 규칙 (표준 SQL 관점)
- `SELECT`에 `SUM(...)` 같은 **집계 컬럼**과 `PRODUCT_NAME` 같은 **비집계 컬럼**이 함께 나오면,
  - 비집계 컬럼은 **`GROUP BY`에 포함**되거나
  - 또는 `MIN/ MAX`처럼 **집계로 감싸**(대표값을 정해)야 한다.
- 이유: 그룹 내부에 값이 여러 개일 수 있는데(이론적으로), DB가 어떤 값을 보여줘야 하는지 **모호**해지기 때문이다.
- 일부 DB는 설정에 따라 “돌아가 보이게” 처리하기도 하지만(임의값 선택 등), 코테/이식성 관점에서는 위험하다.

#### 3. `GROUP BY PRODUCT_ID`만으로 충분한가? (함수적 종속/1:1 관계)
- `PRODUCT_ID → PRODUCT_NAME`이 **항상 1:1로 보장**(예: `FOOD_PRODUCT.PRODUCT_ID`가 PK)된다면 논리적으로는 `PRODUCT_ID`만 그룹핑해도 `PRODUCT_NAME`은 결정된다.
- 다만 DB/설정마다 이 “함수적 종속”을 얼마나 엄격히 인정하는지 달라서, 코테에서는 **안전하게 `PRODUCT_NAME`도 `GROUP BY`에 포함**하는 패턴이 흔하다.
- 더 깔끔한 방식: **(1) 주문 테이블에서 `PRODUCT_ID`로 먼저 집계 → (2) 그 결과를 `FOOD_PRODUCT`와 조인해 이름을 붙이기**.

#### 4. DATE 컬럼 필터링: `LIKE`보다 “날짜 범위”가 안전
- `PRODUCE_DATE`는 DATE 타입이라 `LIKE '2022-05%'`는 DB에 따라 **암묵적 형변환**에 의존해 깨질 수 있다.
- 보통은 `>= 2022-05-01` AND `< 2022-06-01` 같은 **반개구간(월 시작 이상, 다음 달 시작 미만)** 범위 조건이 안정적이고, 인덱스 활용에도 유리하다.

### 실수했던 부분

**1. 조건 컬럼 혼동 (생산일자 vs 출고일자)**

| 틀린 것 | 올바른 것 |
|---------|-----------|
| `OUT_DATE`로 5월 조건을 걸기 | 문제 요구는 `PRODUCE_DATE`가 2022년 5월 |

**2. GROUP BY 누락**

| 틀린 것 | 올바른 것 |
|---------|-----------|
| `SUM(...)` + `PRODUCT_ID/NAME`를 같이 SELECT하면서 GROUP BY 없음 | 상품별 집계를 원하면 `GROUP BY PRODUCT_ID, PRODUCT_NAME` 필요 |

**3. DATE 타입에 LIKE 사용 주의**

| 틀린 것 | 올바른 것 |
|---------|-----------|
| `PRODUCE_DATE LIKE '2022-05%'` (암묵 변환 의존) | 날짜 범위 조건(예: 2022-05-01 이상, 2022-06-01 미만) |

## AI 코드 리뷰

### 개선할 점

1. **날짜 필터는 범위로 처리**: DATE 컬럼에 `LIKE`를 쓰면 DB/설정에 따라 암묵적 형변환에 의존할 수 있고, 인덱스 활용에도 불리할 수 있다.
2. **집계 단계와 차원(이름/가격) 붙이기 분리**: `PRODUCT_ID`로만 먼저 집계한 뒤, `FOOD_PRODUCT`와 조인하면 읽기 쉽고 “왜 GROUP BY에 NAME까지 넣어야 하지?” 같은 고민도 자연스럽게 사라진다.

## 수정된 코드
```sql
SELECT
    P.PRODUCT_ID,
    P.PRODUCT_NAME,
    P.PRICE * S.TOTAL_AMOUNT AS TOTAL_SALES
FROM (
    SELECT
        PRODUCT_ID,
        SUM(AMOUNT) AS TOTAL_AMOUNT
    FROM FOOD_ORDER
    WHERE PRODUCE_DATE >= TO_DATE('2022-05-01', 'YYYY-MM-DD')
      AND PRODUCE_DATE <  TO_DATE('2022-06-01', 'YYYY-MM-DD')
    GROUP BY PRODUCT_ID
) S
JOIN FOOD_PRODUCT P
  ON P.PRODUCT_ID = S.PRODUCT_ID
ORDER BY TOTAL_SALES DESC, P.PRODUCT_ID ASC;
```
